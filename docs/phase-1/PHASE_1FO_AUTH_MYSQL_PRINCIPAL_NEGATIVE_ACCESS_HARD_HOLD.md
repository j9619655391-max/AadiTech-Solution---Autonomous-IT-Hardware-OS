# Phase 1FO — authenticated MySQL principal boundary and zero-row denial (HARD HOLD)

Date: 24 November 2026 (IST). **Internal engineering only.** This is not an independently validated production security architecture or permission to run a migration.

## Concrete gap

Phase 1FL introduced separately configurable auth-vs-runtime database pools, but two different environment-variable strings are not evidence that MySQL authenticated two distinct principals, activated no roles, or denied the general runtime credential access to protected authentication tables. The existing 1FC–1FJ runtime grant gate reviews the *general* connection but cannot establish the dedicated auth connection's actual identity or minimum functional permission. An operator could accidentally configure stale/aliased usernames, inherited default roles, mis-scoped table access, or a misleading `AUTH_DB_USER` claim.

## Bounded internal control

- New `checkStagingAuthPrincipalBoundary` in `scripts/staging-preflight.ts` obtains two checked-out connections: one runtime, one independently configured auth candidate. It verifies `CURRENT_USER()`, `DATABASE()`, and `CURRENT_ROLE()` on **each actual session**, ensuring that each principal is non-empty, has the expected exact username with a MySQL host suffix, uses the same expected schema, has no activated roles (`NONE`), and is distinct from the other principal. Invalid expected identifiers fail before any connection attempt.
- Its only protected-table probe is `SELECT id FROM auth_users LIMIT 0`. The **runtime connection must return a recognized MySQL access-denied error**, while the **auth connection must be permitted**. It never fetches password hashes, MFA secrets, live user IDs, or business rows. Other error classes, successful runtime reads, and auth permission denial all fail closed. Both connections release in `finally`, including when auth acquisition or SQL fails.
- `staging:preflight` checks this only for an explicitly opted-in isolated TLS staging target with configured, non-identical `AUTH_DB_USER` and `AUTH_DB_PASSWORD`. The candidate account uses the same verified TLS configuration as the runtime connection. The status `authPrincipalBoundary` is `PASS | HOLD | NOT_EVALUATED_CI`. When technically observed, only **truncated SHA-256 account fingerprints** are output, never raw usernames, credentials, grants, or protected data. Observation errors are not echoed.
- **Staging `ready` remains false**, and `authFunctionalSeparationVerified=false` and `independentDbaApprovalVerified=false` remain unchanged, even when the narrow identity/zero-row probe succeeds.
- `tests/staging-preflight.test.ts` supplies adversarial mock sessions for wrong identity, wrong schema, active role, absent/duplicate identity records, shared principal, runtime table readability, auth denial, unexpected SQL errors, and connection cleanup. `tests/fc-runtime-db-privileges-mysql.integration.ts` exercises the same exported observer with independently authenticated, temporary read-limited MySQL users in disposable `aaditech_ci`, without changing staging/production grants. Its normal negative read controls remain in place.

## Remaining critical gaps

1. **Full runtime/auth functional split is unimplemented.** CRM and other business mutations still lock `auth_users` inside a runtime transaction, which conflicts with denying general-runtime access to protected tables. Changing the lock into a nontransactional authentication call would permit demotion/revocation races. Do not weaken either the role lock or protected-table denial to force a superficial staging PASS.
2. A one-column, zero-row SELECT probe plus point-in-time metadata **does not prove complete absence of other column privileges, views, routines, inherited roles, proxy users, definer rights, global privileges, or changes after observation**. The 1FB grant observer, external DBA inventory, mandatory-role review and routine/definer audit remain separate mandatory controls. This candidate only adds another fail-closed condition.
3. A real externally authorized DBA and Security reviewer must provision independently attested least-privilege accounts and source-bound secrets, audit all effective and delegated grants, and demonstrate auth/MFA/session/reviewer/CRM operations under actual restricted credentials with concurrency, BOLA/IDOR, CSRF and signed staging/DR evidence. No third-party authorization, legal/KYC evidence or signed provider trust can be inferred from CI.
