# Phase 1FN — M16 internal service-ticket foundation (PRODUCTION HARD HOLD)

Date: 24 November 2026 IST. Branch `chore/phase0-foundation-20261106`, Draft PR #1. This changes M16 from legacy-only preview to a **bounded, real MySQL-backed internal ticket foundation**, NOT completed AMC/service-desk acceptance or external customer support.

## Delivered architecture

1. **Additive migration** `database/migrations/0049_fn_service_tickets_internal.sql` creates `service_tickets_internal` and `service_ticket_audit_internal`, with InnoDB actor/customer foreign keys, owner/customer indexes and unique `(ticket_id,version_after)` audit ledger constraint. First-party status state is limited to `OPEN_INTERNAL`, `TRIAGED_INTERNAL`, `WAITING_INTERNAL`, `RESOLVED_HELD`; there is deliberately **no external CLOSED, technician DISPATCHED or SLA_MET state**. `customer_consent_state ENUM('UNVERIFIED')` and `external_dispatch_state ENUM('DISABLED')` prevent application-level claims of actual customer consent or notification.
2. **Migration custody** `scripts/migrate-service-tickets.ts` permits only `CRM_TEST_DB=1, DB_NAME=aaditech_ci, NODE_ENV=test, DB_SSL=false` disposable CI or explicitly approved isolated `aaditech_staging_*` TLS staging with `SERVICE_TICKETS_MIGRATION_APPROVED=YES`, `STAGING_DISPOSABLE_CONFIRMED=YES`, `NODE_ENV=staging`. It acquires the shared migration lock, verifies all 48 existing migration checksums, applies new 0049 once and refuses checksum drift or unknown migrations on rerun. Registry `scripts/lib/stagingPreflight.ts` now includes 0049. There is **no approved production migration path** in this script.
3. **Boundary validation** `server/serviceDesk/validation.ts` requires a valid CRM customer UUID, one of the 20 existing [Windows troubleshooting guides](PHASE_1FM_WINDOWS_TROUBLESHOOTING_GUIDANCE_HARD_HOLD.md), bounded free-text title and description, `LOW/NORMAL/HIGH` priority, and explicit acknowledgement that actual customer consent is **not verified**. It rejects browser-submitted status, consent verification, dispatch flags, arbitrary identity fields, malformed text, and unauthorized status jumps. Transitions are strictly `OPEN_INTERNAL → TRIAGED_INTERNAL → WAITING_INTERNAL → TRIAGED_INTERNAL`, or `TRIAGED_INTERNAL → RESOLVED_HELD`. HELD is terminal until a separately designed and approved customer-signoff workflow.
4. **Owner-only internal API** `server/serviceDesk/router.ts` and `server.ts` expose `GET /api/service-desk/internal-tickets` (last 100 owner-scoped tickets), `GET /api/service-desk/internal-tickets/:id` (version history), `POST /api/service-desk/internal-tickets`, `PATCH /api/service-desk/internal-tickets/:id/status`. All routes enforce the existing secure owner session (CSRF on writes), `no-store`, strict input. The **same MySQL transaction** locks `ACTIVE OWNER` in `auth_users FOR UPDATE` before writes and verifies a currently active customer with that actor's transactional `crm_audit_events CREATE` provenance. All read/update queries require that same owner. Other owners and absent provenance see 404. Mutation rows and matching append-only audit event commit or rollback together; stale `expectedVersion` is 409.
5. **Actual application UI** `src/components/LiveServiceDeskWorkspace.tsx`, `src/components/Header.tsx`, `src/App.tsx` introduce an **Internal Service Desk** navigation tab. It loads owner-visible CRM customers and 20 known topics, accepts internal observations, lists up to 100 owner-owned internal tickets, and offers only valid versioned transitions and internal audit history. It prominently labels that customer consent, warranty/RMA entitlement, real support SLA and physical repair are **unverified**. No outbound messaging, remote Windows controls or claim of actual repair exists in this interface.
6. **Tests and release custody** `tests/fn-service-tickets.test.ts` exercises migration target, strict consent/fields and transition policy; `tests/fn-service-tickets-mysql.integration.ts` creates synthetic independent OWNER/OWNER/REVIEWER logins, provably owner-created/foreign/forged CRM records, real HTTP ticket lifecycle, foreign-owner object denial, reviewer denial, stale version rollback, 1–5 monotonic audit versions, failed terminal state, disabled OWNER write denial, and MySQL `FOR UPDATE` race with in-flight role demotion. `bun run db:migrate:service-tickets` (twice) and `bun run test:service-tickets-mysql` are required in MySQL CI. BV/BW custody manifests include API/schema/UI/tests. `tests/staging-preflight.test.ts` accepts the checksum-locked 0049 registry.

## Remaining limitations and acceptance

- This is **internal operator-entered observation only**, not a verified customer request/consent, AMC renewal, real contractual SLA, authorized technician scheduling/dispatch, on-site work order, RMA claim, OEM warranty claim, ticket attachment storage, signed customer acceptance or automatic device diagnosis/repair. `RESOLVED_HELD` is not customer-accepted closure.
- Actor-scoped CRM `CREATE` audit is provisional application access provenance, **not corporate legal tenancy or customer authorization**. No verified customer consent/evidence provider or customer self-service access exists. Avoid putting credentials, passwords or regulated information into free-text notes.
- Known Phase 1FL conflict persists: a restricted general runtime MySQL principal cannot satisfy Phase 1FH denial of SELECT on `auth_users` while M03/M04 and 1FN write transactions depend on `auth_users FOR UPDATE` to serialize role demotion. Need separately designed atomic authorization authority service or approved stored procedure with audited SQL least privilege and functional TLS staging end-to-end, plus independent DBA/Security sign-off. Green disposable root-credential CI alone **does not prove a deployment-usable least-privileged service architecture**.
- M16 acceptance status becomes **`SERVER_INTERNAL_HELD`** in `REMAINING_M01_M30_ACCEPTANCE_LEDGER.json`; `externalApprovalRequired=true`, `signedAcceptanceEvidence=null`, `realExternalAuthorityVerified=false`, `productionEnabled=false`, `releaseDecision=HOLD`. M01–M30 legal, business, installer, data governance, independently witnessed encrypted DR, real provider trust, WORM/CAS and protected main/non-author approvals remain open.
