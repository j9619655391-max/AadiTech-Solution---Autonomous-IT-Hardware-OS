This **does not tell us** whether the two usernames belong to legally appointed Security and Business corporate officers, whether a corporate registrar is genuine, whether MCA signatory delegation exists, whether keys are independently enrolled, or whether an external eMudhra/CCA/RCAI provider signed or revoked anything. Phase 1DM establishes the strict **cross-interface contract** needed to compare candidate corporate appointments and key possession with the 1DL source continuity, while keeping both modules unable to promote a synthetic/offline packet into actual legal authority.

## Phase 1DM implementation

New `scripts/phase1dm-corporate-appointment-challenge-handoff.mjs` exports a **pure, offline, read-only** `assessOfflineCorporateAppointmentCandidate` and `candidateSigningBytes`. The only accepted inputs are an exact-schema candidate packet, two expected out-of-band **public** pins (registrar Ed25519 SPKI SHA-256 and corporate registry evidence SHA-256), the already existing 1DL **terminal in-memory receipt**, two operator-nominated GitHub reviewer names (not printed), and a strict validation clock.

1. **Exact signed candidate** must contain repository, source SHA and pinned base-main SHA, organization/registry digest, a nonzero 256-bit nonce, exact two role-ordered officer records, explicit `HOLD`, and canonical ISO times with a maximum 15-minute validity interval. The root's signature uses a separate `ROOT` Ed25519 domain. Unexpected GO flags/fields, malformed/oversized packets, stale signatures, noncanonical encoding and modified signed bytes fail closed.
2. **Distinct registrar/Security/Business Ed25519 public keys**, exact verified SPKI DER hashes, unique key IDs and segregated roles. Two further signed and domain-separated officer **proofs of key possession** each bind the registrar-signed appointment SHA-256, GitHub login, source HEAD/main, organization, challenge nonce, officer role, assertion time, and `HOLD`. Changing role labels, login, key, nonce, timestamp or source prevents mathematical acceptance.
3. The original Phase **1DL terminal technical continuity receipt** is required to contain exact source/main, completed source/role continuity and permanent HOLD. No direct GitHub API calls, reviewer requests, external provider credentials, candidate root enrollment, external key-signing, CI workflow edits, or privileged writes are added.
4. All output fields are **technical booleans, validated signature count, source SHAs and anomaly codes**. No GitHub logins, PEM keys, signatures, nonce, raw company registry digest or private key leaves the memory-only verifier. Reports always carry `productionReleaseAuthorized=false`, `productionReleaseBlocked=true`, `releaseDecision=HOLD` and `independentLegalCorporateRegistrarRootAuthorityAuthenticated=false`, even when a fully applicant-generated packet verifies mathematically.
5. The new module is a **contract for future approved human-operated intake**, not a connected onboarding CLI. It cannot independently distinguish an authentic legal registrar from an attacker who supplies both a self-controlled signing key and the matching comparison pin. Nothing may interpret `candidateCorporateRegistrarAndTwoOfficerProofsStructurallyConsistentOnly=true` as independent corporate appointment, staging acceptance, release GO, current provider certificate, CRL/OCSP or audited WORM proof. Until independent legal/provider registration and authenticated signing keys exist, production remains HARD HOLD.
