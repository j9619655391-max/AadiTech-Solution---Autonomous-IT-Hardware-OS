## Verified public basis, NOT completed real onboarding

The Controller of Certifying Authorities (CCA) publishes [eMudhra CA as a licensed CA](https://cca.gov.in/CAServicesPublic.html); the CCA also explains how [RCAI public keys authenticate licensed CAs](https://www.cca.gov.in/avail_service.html) and [RCAI CRL and OCSP services](https://cca.gov.in/services.html). CCA hosts an [eMudhra Certificate Practice Statement (CPS) v4.2.0](https://cca.gov.in/sites/files/pdf/Licensed-CA/eMudhra%204.2.0_signed.pdf) with certificate-policy, permitted issued profile, identity verification and CRL/OCSP context. eMudhra's separate [emCA product REST API documentation](https://emca.emudhra.com/integrating-emca/rest-api-support) describes certificate/eSign management APIs, but publicly documented product API access is **not proof this application has a licensed-ca sandbox account, contract, authorized API scope or permission to use those endpoints**. These documents are reference materials; legal counsel and security must independently validate whether they apply to intended supplier ACK/warehouse GRN use.

**No real eMudhra agreement, authorized sandbox credentials, independently authenticated RCAI-to-eMudhra certificate chain, provider-issued supplier certificate, authoritative CRL/OCSP publisher, official MCA corporate registry attestation or legally authorized signer mandate has been supplied.** The project has not contacted eMudhra, CCA, MCA, a supplier or a warehouse. There is **no live provider connection, KYC certification or actual sandbox authorization**. Synthetic OpenSSL certificates, CA signatures and locally generated CRL/OCSP are test fixtures only. They are not evidence that an actual provider, company, authorized individual or GRN is authenticated. This release intentionally delivers **approval-gated prerequisites**, not activation.

## Sequence: offline and internal, never externally authoritative

1. **Original Phase 1AN nomination** must be separately internally `REVIEWED_CANDIDATE_HELD` for the fixed publicly listed eMudhra evaluation candidate. Phase 1AN sandbox access gate continues `NOT_CONFIGURED/NOT_VERIFIED/DISABLED/HOLD`.
2. **OWNER creates packet** `POST /api/provider-onboarding/packets` with exact `nominationId`, `contractDocumentSha256`, `providerOnboardingRef`, `sandboxScopeRef`. No private agreement, API credential, token, commercial secret, personal data, signed government ID or raw KYC file enters API.
3. **Two different REVIEWERS** independently call `POST /api/provider-onboarding/review/packets/:id/decide`; one LEGAL and one SECURITY. Both require CSRF, session role, recent-password step-up, configured privileged MFA, written reasons, evidence tickets, `noExternalContractAcknowledged=true` and `noLiveCredentialsAcknowledged=true`. The DB forbids one reviewer performing both reviews. Two positive reviews move only to `DUAL_REVIEWED_HELD`; a rejection remains permanently internal rejected.
4. **OWNER's pinned-policy trial** `POST /api/provider-onboarding/trials` requires the two reviews and original Phase 1AN independently reviewed policy and Phase 1AM one-hop certificate; rechecks the Phase 1AL signed *candidate* revocation source, current root pin/issuer fingerprint and that both certificate hashes match the original source. Only a locally bounded `OFFLINE_CRYPTO_HELD` record is created. Phase 1AN OpenSSL `-x509_strict -explicit_policy` dry-run is strictly isolated nonproduction. There is still no real RCAI/eMudhra hierarchy or independently sourced CP OID.
5. **Offline CRL signature:** `POST /api/provider-onboarding/revocations` accepts `artifactType='CRL'`, `trialId`, and canonical base64 of signed X.509 CRL DER (≤64 KiB). In disposable CI or explicitly approved isolated TLS staging ONLY, OpenSSL `crl -verify -CAfile <pinned public root>` revalidates CA signature, then `openssl verify -crl_check -CAfile <root> -CRLfile <crl> <leaf>` refuses a revoked/expired/not-yet-valid leaf or CRL. Temporary files contain PUBLIC X.509 and signed revocation data only, are mode 0600, and are deleted after use. No network call is made. This does **not** authenticate the actual provider's CRL issuer; result is `SIGNED_OFFLINE_HELD`.
6. **Offline OCSP signature/status:** The same endpoint accepts `artifactType='OCSP'` with bounded DER. The isolated adapter runs `openssl ocsp -respin <der> -issuer <pinned public CA> -cert <leaf> -CAfile <public root> -no_nonce -validity_period 300 -status_age 3600`. Return must include verified responder signature and `leaf: good`. Captures stdout **and stderr**, checks exit code, timeout (4 s), output size and interprets no warnings as an actual provider publisher guarantee. This verifies only mathematically that the synthetic pinned CA responded on the particular serial; it does **not** independently authenticate an external OCSP responder or prove actual legal issuer authority. Reject stale, tampered, unknown or revoked status. CRL and OCSP must both be independently reviewed as `CRYPTO_REVIEWED_HELD`, with missing publisher/CA provenance explicitly acknowledged.
7. **MCA/signatory evidence** `POST /api/provider-onboarding/mca-evidence` references the exact original Phase 1AN already internally inspected dossier. It stores only two 64-hex SHA-256 values of alleged MCA and delegated signer records, and an internal ticket; it never queries MCA or claims actual legal authority. Independent REVIEWER `/review/mca-evidence/:id/decide` must acknowledge `externalMcaAuthenticationMissingAcknowledged=true` and `signatoryAuthorityMissingAcknowledged=true`; positive outcome is `INTERNALLY_INSPECTED_HELD`.
8. **Readiness** `GET /api/provider-onboarding/readiness?trialId=...&mcaId=...` repeats all original Phase 1AN reviewer/policy/corporate source checks, up-to-date Phase 1AL candidate-signed revocation, pinned leaf certificate check and two OFFLINE signed CRL/OCSP snapshots and one MCA reviewer decision, all under MySQL transaction/row locks. A later signed candidate revocation forces 409; a changed PEM, DER hash, provider pin, reviewer identity or unauthorized state also denies. Even if all isolated math passes, response always includes `actualProviderContractVerified=false`, `approvedSandboxCredentialsPresent=false`, `independentMcaCorporateIdentityVerified=false`, `trustedCAIdentityVerified=false`, `authenticatedExternalCrlOcspPublisher=false`, `fullRfc5280ProductionPath=false`, `productionReady=false`, `stockPostingEnabled=false`, `officialGrnVerified=false`, `availableToSell=null` and full real-world blockers.

**Cert-policy scope:** These public fixtures use Ed25519 direct CA-to-leaf one-hop and test OID `1.2.3.4.5`. Actual India PKI may involve RCAI + CA/sub-CA and different algorithms/OIDs. The code does not pretend a synthetic direct root signature satisfies CCA/eMudhra real chain or provider-specific certificate EKU, name constraints, certificate policies, real organizational-person identity or key-custody assurance. Real-world provider-published CRL/OCSP must be evaluated with their authorized issuer chain, responder delegation, trusted HTTPS/provenance, expected issuer/serial/nonce and policy before any operational acceptance. No production PKIX validation is enabled.
