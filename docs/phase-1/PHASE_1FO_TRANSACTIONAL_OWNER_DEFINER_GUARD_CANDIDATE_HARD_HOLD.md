# Phase 1FO — Restricted runtime OWNER guard: same-transaction SQL SECURITY DEFINER candidate (HARD HOLD)

Date: 24 November 2026 IST. Branch `chore/phase0-foundation-20261106`; Draft PR #1 remains unmerged. This is a **synthetic CI + application-code enforcement candidate**, not a provisioned staging principal, trusted DBA-owned routine, completed privilege split or authorized production release.

## Pre-existing architectural conflict

Phase 1FL introduced separate runtime and authentication connection pools. Phase 1FH prohibits the general application runtime account from reading or mutating secret-bearing `auth_users`, sessions, MFA and reviewer authority tables. However Phase 1FD CRM, Phase 1FK quotation CREATE/revisions and Phase 1FN internal service tickets previously called `SELECT role,status FROM auth_users WHERE id=? FOR UPDATE` directly inside the general runtime transaction to prevent post-middleware OWNER role demotion/disable races.

Simply moving that role check to an independent auth-pool connection **would lose same-transaction serialization**, reopening a time-of-check/time-of-use race. Giving the runtime raw `auth_users SELECT` or schema-wide DML violates least privilege. A separate, narrowly controlled routine capable of taking the **same InnoDB row lock on the original runtime transaction** is the bounded candidate here.

## Implemented source changes

- `database/authority/phase1fo_active_owner_guard.sql` is a small **readless-to-caller** `SQL SECURITY DEFINER` procedure, `aaditech_guard_active_owner(IN p_actor CHAR(36))`, that issues `SELECT role,status ... FOR UPDATE` internally, `SIGNAL SQLSTATE 45000` for missing/disabled/non-OWNER, and emits **no result set containing identities, password hashes or MFA material**. It does not itself GRANT EXECUTE, create/change users, mutate roles, send messages, make releases or self-install. The install is deliberately **not in the automatic 0001–0049 schema migration registry**.
- `server/crm/repository.ts` central `lockActiveCrmOwner` now supports **`AUTH_OWNER_GUARD_MODE=procedure`**. The same transaction issues one parameterized `CALL aaditech_guard_active_owner(?)`. A single precise `ER_SIGNAL_EXCEPTION` + `45000` + `AUTH_OWNER_INACTIVE` maps to the existing generic 403, while **missing routine/grant, metadata drift, deadlocks, lock timeout, malformed mode and other database errors fail closed**. **Staging/production require procedure mode**; no fallback to privileged `SELECT` is allowed. Local disposable CI and development may still use the existing direct mode unless explicitly opting into the new integration test. All three existing CRM/quotation/ticket routes reuse this single helper without routing around their transaction.
- `scripts/phase1fb-runtime-db-privileges.ts` continues to reject all direct protected-table SELECT/DML, schema-wide grants, active roles, VIEW grants, unknown SQL object quoting and DDL. It now recognizes **at most one** exact `GRANT EXECUTE ON PROCEDURE <schema>.aaditech_guard_active_owner`, rejecting unrelated/renamed routines, FUNCTION grants, wildcard EXECUTE and ALTER ROUTINE. `verifiedRuntimeDefinerOwnerGuard` requires one same-schema `ROUTINE_TYPE=PROCEDURE, SECURITY_TYPE=DEFINER` metadata target.
- `scripts/staging-preflight.ts` checks `AUTH_OWNER_GUARD_MODE=procedure` and the routine's exact grant and same-session routine metadata for restricted staging. It still **always reports real staging NOT READY** until independent DBA-attested installation, signed body/definer control, real restricted account end-to-end and broader M01–M30 acceptance are proven. Synthetic tests do not grant real credentials.
- `tests/fo-definer-owner-guard.test.ts` covers direct fallback prevention, exact grant parser/metadata, malformed/duplicate/broader permissions and missing routine or lock timeout fail-closed paths. `tests/fo-owner-guard-mysql.integration.ts` is restricted to fresh disposable `aaditech_ci`: creates a controlled routine and a random SQL runtime principal **without auth_users permissions**, grants only explicitly named business tables and the exact PROCEDURE EXECUTE, then exercises real authenticated Express HTTP CRM customer/product CREATE, quote draft, internal service ticket CREATE/transition using a **separate auth database pool**, verifies raw protected-table SELECT/UPDATE denial and the same-connection MySQL privilege preflight, and races a role-disable update against a runtime CALL to ensure it cannot leapfrog the lock. All temporary test routine/user/session are isolated to CI and cleaned up.
- New `bun run test:fo-owner-guard-mysql` GitHub Actions job; 1BV/1BW source custody includes procedure, new unit/integration tests and existing tracked runtime privilege/quote/CRM/ticket/CI files.

## Important limitations / required independent acceptance

This is **not** an automatically installed or approved privileged database routine. A human DBA must independently review the **exact** SQL bytes and routine `DEFINER` account, verify least privilege for that definer, independently provision mutually distinct runtime/auth/authority principals, grant **only** per-procedure EXECUTE, verify no privilege widening via grants, roles, other routines or views, independently inspect installed `SHOW CREATE PROCEDURE`, and attest immutable signed/WORM evidence. Metadata alone **cannot authenticate the routine body or who actually controls the DEFINER**. There is no provisioned, independently secured TLS staging/production database in this phase. Actual end-to-end readiness under approved separated credentials, field Windows installer/Hostinger verification, customer/tenant legal access, and any real release remains outstanding.

A compromised runtime principal granted this procedure could still request locks against arbitrary known UUIDs, potentially affecting availability; it cannot read auth row contents through the procedure, but availability/rate-limit design and DBA resource policy require separate review. The connection must hold the caller's transaction until commit/rollback and **must not connect through an SQL proxy that breaks session affinity**. The existing transaction role lock still works during development and disposable CI with direct mode; this does not confer production trust.

**Phase 1FO CI acceptance policy:** Only exact final branch-HEAD push **and** Draft-PR workflow `COMPLETED/SUCCESS`, with a genuine isolated MySQL reduced-privilege SQL user and actual HTTP/race tests, can mark the synthetic engineering candidate verified. Historical CI red/runner failures must be retained. This is not independent DBA approval, legally trustworthy customer consent, or production deployment.
