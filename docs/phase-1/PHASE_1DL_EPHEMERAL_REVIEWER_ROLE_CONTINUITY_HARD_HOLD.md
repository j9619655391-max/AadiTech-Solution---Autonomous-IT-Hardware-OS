## Practical source-binding flaw

Previous human-only 1DG CLI receives two named GitHub reviewer logins and invokes the Phase 1CO read-only reviewer-evidence observer twice, reconciles those two counts/booleans in Phase 1DF, checks the pinned base-`main` CODEOWNERS owner pair, then re-reads Phase 1CO between final official 1DC governance reads and joins the Phase 1DI report. None of the *boolean-only* 1CO/1DF/1DI source-bound receipts previously carried a cryptographic continuity marker for **which exact login played Security and which played Business** across the initial and final evaluations. In a composition or substituted receipt attack, two different pairs of GitHub accounts might each satisfy the same two-approval counts and be inadvertently treated as the same role-specific reviewers. CODEOWNERS pair order is role-independent, but Security/Business officer identity assignments are **role-dependent**. The real operator currently calls the same input variables; this hardening makes the invariant explicit and machine-checkable.

## Concrete implementation

- New `scripts/phase1dl-ephemeral-reviewer-handoff-continuity.mjs` exports `deriveEphemeralReviewerRoleBinding` and `assessEphemeralReviewerHandoffContinuity`. Both are **read-only pure functions**. A genuine human operator's process generates one fresh **32-byte local cryptographic random** `sessionKey` (no CLI or repository-supplied secret); the HMAC-SHA256 preimage is domain-separated and binds exact repository, PR #1, development branch, `main`, **actual PR source HEAD and main SHA**, role label and normalized login in **strict Security/Business order**. Using a secret-keyed MAC avoids publishing a plain unsalted predictable-username hash. The **key is not logged, persisted or transmitted**; session-specific HMAC is not a corporate signature or external attestation.
- `scripts/phase1co-live-exact-head-reviewer-quorum.mjs` accepts **optional** `nomineeSessionKey` and attaches `opaqueReviewerRoleSessionHmacSha256` **only after** its actual two nominated current-head approvals, complete pagination and independently read GitHub repository permissions pass. Existing CI evidence and public no-key readers remain valid and continue emitting `null` binding rather than pretending a live operator session occurred. GitHub read-only GET paths stay fixed.
- `scripts/phase1df-role-bound-readonly-reconciliation.mjs` adds optional `requireRoleContinuity=true` to require two actual 1CO readbacks to carry the **same valid 64-hex session HMAC** and records a fail-closed `DL_TWO_REAL_ROLE_APPROVAL_READS_NOT_SAME_NOMINEE_SESSION` on mismatch. Its explicitly **human-only** CLI now generates one key and enforces this requirement. The test-oriented pure function defaults to old behavior when no key supplied, but **the operator command does not**.
- `scripts/phase1dg-effective-codeowners.mjs` explicitly generates a fresh key **once per operator invocation**, carries it through the two initial 1CO observations, mandatory 1DF role continuity, the third terminal 1CO observation, the exact pinned CODEOWNERS/1DI rechecks, and finally executes the 1DL in-session verifier, refusing any mismatch with a nonzero exit code. The final report is only `{codeowners,terminal,continuity}`: booleans/anomaly codes and source SHAs, **no usernames, MAC, session key, operator token, or raw review/policy body**. `main` remains untouched, no requests/reviews/configuration writes are enabled.
- **30 adversarial Node test groups** `tests/phase1dl-ephemeral-reviewer-handoff-continuity.test.mjs` cover real `assessRealNonauthorApprovalQuorum` output, 1DF strict binding, 1DG pinned-file synthetic Git blob, 1DI review-history join, role swapping, different session key, different exact HEAD/main SHA, missing/invalid key, malformed HMAC, substituted initial/terminal receipts, spoofed booleans, incomplete actual permission/quorum, CODEOWNERS and 1DI weakened source, output secrecy, CI/operator wiring and permanent HOLD. The new source/test and modified files are registered in both Phase 1BV build input and Phase 1BW review-source custody inventories, with **no new workflow permission**.

## Non-goals, human authorization and hard stop

An **operator-local HMAC** is not an independent third-party signature, issuer certificate, corporate mandate, legal appointment, cryptographic proof of GitHub's user identity, signed external WORM/DR record or post-run audit receipt; it is deliberately **ephemeral and not reproducible by external investigators without the private in-session key**. It prevents accidental or malicious *in-process role binding swaps* in the explicit read-only workflow, but cannot defeat a compromised operator process or self-asserted authorizing roles. It must never be logged or persisted. An actual user name in GitHub still needs independently verified corporate Owner/Legal nomination and separately verified identity documents.
