**Date:** 2026-11-16. **Development branch:** `chore/phase0-foundation-20261106`. **Production:** **HARD HOLD**. **Scope:** security engineering and synthetic Ed25519 signature-verification testing; **NOT** approved provider enrollment, real signer/key authentication or production acceptance.

## What this phase fixes

Phase 1AV introduced a self-hashed 64-event maximum administrative incident journal. An operator can recompute all its SHA-256 hashes after replacing the complete history, so those hashes **cannot** establish externally authenticated immutability. Phase 1AW adds a separately pinned public-key, detached-signature **verification readiness layer** binding exact journal state, exact Phase 1AU candidate-policy claims and an optional recovery claim. It tests tamper, expiry, rollback and role-separation failures, without ever promoting a synthetic checkpoint to real trusted authority.

**Trust boundary:** A locally valid Ed25519 signature proves only that a private key corresponding to the *supplied, locally pinned public key* signed a specific byte sequence. It does **not** prove the provider issued that key, an actual LEGAL/SECURITY representative owns it, a timestamp is trusted, a signed agreement exists or a provider-licensed RCAI/CCA certificate chain has been authenticated. This code deliberately exposes all those external authority fields as **false**.

## Engineering implementation

1. `scripts/lib/phase1AwSignedCheckpoint.mjs` accepts a **strictly scoped checkpoint** with version 1; fixed evaluation provider and sandbox purpose; sequence and canonical-millisecond UTC issue/expiry; predecessor checkpoint SHA-256 or null genesis; exact Phase 1AV incident event count and tail SHA; normalized digest of the validated Phase 1AU administrative policy snapshot; optional bound recovery SHA; and literal `releaseDecision: HOLD`. Extra fields such as `productionReleaseAuthorized`, credentials or arbitrary trust flags **fail closed**.
2. Domain-separated **Ed25519 detached signatures** must appear in exact LEGAL, SECURITY order with distinct opaque reviewer refs and key IDs. A **separately supplied** two-entry reviewer-key pin configuration, not any key inside the untrusted checkpoint, must match role, reviewer ID, key ID and SHA-256 of canonical SPKI DER. Only bounded, public Ed25519 SPKI PEMs are accepted; no private keys, RSA substitution, weak or unspecified signature algorithms. Every checkpoint is signed over a fixed ordered field list and purpose-specific byte prefix, preventing replay of the same signatures as service/stock/finance instructions.
3. Signatures are validated using Node.js `crypto.verify(null, message, pinnedPublicKey, ed25519Signature)`. Invalid detached signatures are reported as blockers; structurally malformed signatures, keys, dangerous unknown fields and scope/sequence errors are rejected. **Signature verification never sets an authority or production gate to true.**
4. A checkpoint is cryptographically bound to the independently parsed Phase 1AV self-hash journal (`eventCount` and tail SHA) and an exact, key-order-independent SHA of the Phase 1AU snapshot after its existing schema/16-digest/window validation. No journal or policy mismatch is silently trusted. A signed checkpoint cannot predate the journal's last event or the policy inventory's `recordedAt`.
5. Checkpoint lifetime max **24 hours**, with canonical UTC dates and a five-minute future-skew tolerance. A checkpoint must be fresh for a *local readiness assessment*; stale signed claims trigger incident quarantine. This is **not** an RFC 5280 certificate-validity or CRL/OCSP freshness determination, nor an authenticated external timestamp.
6. Previous/current checkpoint comparison requires exact predecessor **receipt** linking (domain-separated SHA over all signed data and detached signatures), sequence increment of one and nondecreasing issue time, plus the Phase 1AV journal prefix and Phase 1AU policy-drift controls. Signature-key rotation is **not trusted or enabled** just because a packet supplies a new public key. Missing predecessor, rewritten old hashes, an invalid prior signature, replay, rollback or journal fork remain HOLD or quarantine.
7. Optional strictly shaped administrative **recovery claim** includes incident reference, four SHA-only restore/MFA/network/revocation-recheck claims, monotonic event chronology, `outboundDispatchHeld:true`, literal `releaseDecision:HOLD` and distinct claimed SECURITY/OPERATIONS/OWNER reviewers who are not incident operators. A recovery claim digest is bound into the **signed checkpoint**, preventing replacement after signing; missing or substituted claims raise explicit blockers. These flags and SHA values are untrusted **claims**, not proof of witnessed restore, MFA recovery, successful CRL/OCSP checks, independent identities or operational release authorization. Closure claims never clear historical quarantine.
8. Zero-input `scripts/phase1aw-checkpoint-preflight.mjs --ci-hold` reads **no private file, secret, key, database or network source** and always prints hard-false authority, issuer, GRN, stock, supplier, finance and production flags with `HOLD`. All other CLI options exit 2 with sanitized diagnostics. The library's public-key checking interface is exercised only with **ephemerally generated synthetic Ed25519 key pairs** in tests; no real key material is added to Git or workflow artifacts.
