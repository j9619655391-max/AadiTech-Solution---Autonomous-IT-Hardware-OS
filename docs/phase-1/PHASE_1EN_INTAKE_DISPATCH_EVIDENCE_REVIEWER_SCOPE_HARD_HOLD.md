## Confirmed BOLA/IDOR threat model

Phase 1EL limited authenticated REVIEWER access to owner-nominated QUOTES and PROCUREMENT. Remaining `/api/intake/review`, `/api/po-dispatch/review`, `/api/evidence-chain/review` returned records for **any other** actor because their old guard was `recorded_by<>actor` or `prepared_by<>actor` only. This exposed supplier emails, dispatch snapshots, physical count references, claims, GRN evidence and allowed foreign-owner decisions by anybody with a valid REVIEWER session. An independent REVIEWER role does not automatically confer access to all owners' private operational records.

- Additive non-backfilling migration `0044_en_workflow_review_scopes.sql` extends pre-existing 0043 ENUM columns on both `app_reviewer_scope_grants` and `app_reviewer_scope_events` by **appending** `INTAKE`, `DISPATCH` and `EVIDENCE` to original QUOTES/PROCUREMENT order; existing grants do **not** expand automatically. No implicit grants, tenant promotion, deletion, external verification, finance/warehouse posting or production approval. Schema 0043 SQL unchanged and its existing hash remains authentic.
- `scripts/migrate-en-reviewer-scopes.ts` validates all 43 previous SHA256 migration bytes and no unexpected schema IDs, acquires the shared MySQL advisory lock, applies 0044 and records byte checksum. The additive ENUM extension is safe to repeat if interrupted between two MySQL DDL statements. Only exact disposable `aaditech_ci` CI or separately explicitly approved isolated TLS staging with `EN_REVIEW_SCOPE_MIGRATION_APPROVED=YES` can run it; no production target. `scripts/migrate-el-reviewer-scopes.ts` still applies its fixed predecessor 0043 under an expanded registry. `stagingPreflight.ts` registers 44 schemas, CI applies 0044 twice and checks idempotency. Unit test `tests/en-reviewer-scope-migration.test.ts` denies unapproved targets and detects schema scope/backfill drift.
- Existing `GET/POST /api/reviewer-scopes` now accepts only five exact internal workflow scope identifiers. OWNER-only POST still requires CSRF, authenticated active REVIEWER user, privileged MFA policy, current-password step-up, transactionally unique owner-scoped grant/revoke and local immutable decision event. No formal corporate independence, MCA appointment or provider approval is claimed.

## Server route authorization

- Intake `GET /observations` and `GET /observations/:id` join observation to its purchase request/supplier/site and require same session-owner provenance and an **ACTIVE INTAKE** grant (literal SQL scope `INTAKE`; no cross-purpose reuse of PROCUREMENT assignment). `POST /observations/:id/witness` checks those parent authors and locks reviewer scope row inside transaction before writing decisions/quarantine custody and serials.
- Supplier dispatch `GET /destinations` / `GET /requests` / `GET /requests/:id` require consistent supplier/request/destination/preparer creator lineage plus active exact `DISPATCH` grant; supplier email and immutable held PO manifests no longer leak through a generic REVIEWER queue. `POST /destinations/:id/decide` and `POST /requests/:id/decide` check current source owner equality and lock the applicable active grant for the entire transaction before review/outbox HOLD writes.
- Supplier acknowledgment and GRN evidence `GET /claims` / `GET /grn-packs` / `GET /grn-packs/:id` check source claim/preparation/request owner and exact active `EVIDENCE` grant. Claim and pack decision POST resolve the trusted held original owner and acquire `FOR UPDATE` grant lock, rejecting revoked/unknown reviewer access as 404 before review/held-GRN creation. Existing cryptographic snapshots, no-real-receipt disclaimers, no physical stock posting and disabled external outbox remain unchanged.

All routes still require authenticated REVIEWER identity and existing current-password step-up/MFA/CSRF for privileged POST. No user-supplied `ownerId` is trusted. Revoke serializes against new writes; reads do not become a credential for future decisions.
