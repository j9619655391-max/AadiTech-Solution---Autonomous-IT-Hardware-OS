# Phase 1AM — Corporate identity/signatory and provider X.509 certificate sandbox evidence

**Date:** 12 November 2026 · **Branch:** `chore/phase0-foundation-20261106` · **Production release:** HOLD

## Outcome and evidence truthfulness

The project can now capture **claimed** corporate registry and authorized-signatory references with SHA-256 document hashes (without original personal documents), independently review these internally and verify a **one-hop, directly issuer-signed X.509 Ed25519 certificate** against a Phase 1AL server-preprovisioned candidate root/public key. The leaf certificate's public key must exactly match the original Phase 1AK independently internally reviewed issuer Ed25519 SPKI. Root certificate must be CA=true, self-signed, use the pinned root SPKI, have valid dates and directly issue/sign the leaf. Leaf must be CA=false, valid and exactly signed by the root public key. A fresh, cryptographically revalidated Phase 1AL root-signed cumulative revocation feed must not list the leaf's SPKI fingerprint.

**These are implementation and sandbox validation prerequisites—not genuine onboarding.** No real provider, approved supplier/warehouse KYC or legally validated authorized signatory has been connected. The user has not supplied a real provider issuer certificate, authenticated CA trust anchor or credential/revocation source. Synthetic test certificates can demonstrate crypto plumbing **but never external identity**. A valid one-hop signature does not establish a complete RFC 5280 certification path, path constraints, name/policy constraints, EKU, key usage, general-purpose CRL/OCSP, authenticated revocation issuer/source or corporate identity. This phase does not silently infer a certificate is legally provider-issued, does not query government/corporate registries and does not contact vendors.

See [RFC 5280, sections 6.1–6.3](https://www.rfc-editor.org/rfc/rfc5280.html) for the much broader certificate path and revocation requirements. For actual issuance authorization a vetted provider-specific policy/adapter and independently sourced root credentials are necessary. **All positive app outcomes are deliberately HELD and nonauthorizing.**

## Ordered workflow and separation of duties

1. **Server-preprovisioned root:** Phase 1AL must have a server-configured Ed25519 root SPKI, matching root SHA-256, separate pinned TLS SPKI and canonical HTTPS DNS origin. Another independent user may only mark the internal pin as `REVIEWED_HELD`, not genuinely authenticate its owner. A frozen pin, missing/mismatched environment pin or invalid provider blocks the entire Phase 1AM chain.
2. **Supplier or warehouse issuer:** The original Phase 1AK issuer candidate must be separately internally reviewed `REVIEWED_HELD`, match exact Phase 1AL pin owner/party purpose and original internal corporate-registration string. A frozen 1AK issuer is not eligible.
3. **OWNER claims documents:** OWNER sends `POST /api/provider-sandbox/cases` with exactly `pinId`, `issuerId`, `purpose`, `registryReference`, `identityDocumentSha256`, `signatoryReference`, `signatoryDocumentSha256` and `evidenceRef`. These are **references to externally handled documentation**, not evidence that this app authenticates legal identity. Backend binds to original internal party and checks exact idempotent replay. Different data for the same case is 409.
4. **Independent case REVIEWER:** `POST /api/provider-sandbox/review/cases/:id/decide` uses a different user, explicit current-password step-up/MFA/CSRF, reason, evidence reference, separate `registryInspected` and `signatoryInspected` attestations. Positive decision is `REVIEWED_EVIDENCE_HELD` only. No legal company representative is verified by this app.
5. **X.509 public certificate package:** OWNER sends exact `caseId`, `rootCertificatePem`, `leafCertificatePem`. Inputs accept one canonical PUBLIC certificate PEM each (≤8 KiB; rejects keys, chains, ambiguous bytes). Node `X509Certificate` rechecks parsed DER: root's SPKI SHA matches the **separately provisioned Phase 1AL root**; root `ca=true`, self-issuer, self-signature and validity window; leaf `ca=false`, direct `checkIssued(root)`, `verify(root.publicKey)`, leaf key algorithm Ed25519, exact leaf SPKI SHA matches the **existing Phase 1AK key**, both cert validity windows current and nested appropriately, distinct root/leaf and valid serial. Public CA and leaf certificate SHA-256 are persisted along with immutable snapshot. This is **one-hop signature matching**, intentionally not general-purpose RFC 5280 certificate path validation.
6. **Independent certificate REVIEWER:** GET `/review/certificates/:id` reconstructs and re-verifies certificate bytes with the current server root and original issuer. Positive `/review/certificates/:id/decide` requires explicit `certificateInspected` and `policyGapsAcknowledged` attestations; it is `REVIEWED_CRYPTO_HELD`, not provider-issued credential acceptance.
7. **Latest signed revocation:** `GET /api/provider-sandbox/readiness/:id` rechecks the entire independent case/cert review, current exact root pin and leaf certificate signature, then calls Phase 1AL `latestFeed` to revalidate Ed25519-signed issuer root manifest, current sequence, canonical payload, expiry and normalized fingerprint entries. If latest provider-root signed feed includes the leaf issuer SPKI fingerprint, or earlier phases have frozen the root/issuer, readiness **409**. If mathematically consistent, readiness returns only technical facts and **`productionReady:false`**.
8. **Evidence recheck:** `POST /api/provider-sandbox/revocation-checks` records only immutable `CHECKED_HELD` snapshot digest bound to the *current* signed feed; same exact snapshot is idempotent; new feed triggers new check; revoked/stale/compromised proofs denied. No outbox dispatch, real GRN or stock authorization is created.

All GETs are session-role-scoped and no-store; mutations require role, CSRF, recent owner/reviewer password step-up and privileged MFA. OWNER and REVIEWER have separate workspaces with irreversible/internal-only confirmation text and no private-key upload field. User-provided raw person/government documents and provider credentials are deliberately not requested.

## Sandbox API contracts and hard limits

- OWNER `GET /api/provider-sandbox/cases`, `POST /cases`, `GET /certificates`, `POST /certificates`, `GET /readiness/:id`, `POST /revocation-checks`, `GET /authority`.
- REVIEWER `GET /api/provider-sandbox/review/cases`, `POST /review/cases/:id/decide`, `GET /review/certificates`, `GET /review/certificates/:id`, `POST /review/certificates/:id/decide`.
- There is no `/authenticate-provider`, `/approve-legal-identity`, `/issue-real-PO`, `/official-grn`, `/post-stock`, `/reserve`, `/payment` or `/release-production` route. No endpoint accepts private keys, flips trusted statuses, emails a supplier or sends a physical instruction. All `/authority` responses explicitly advertise disabled production and unverified identity.
