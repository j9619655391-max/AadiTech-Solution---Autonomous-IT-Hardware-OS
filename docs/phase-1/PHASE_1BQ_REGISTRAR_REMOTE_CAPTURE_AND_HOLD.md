## Goal and explicit non-authority boundary

Phase 1BP validates internally configured four-role signed **candidate** evidence but does not independently attest signer legal identities, CA enrollment, remotely retrieved signed checkpoints, cloud Object Lock or real disaster recovery. Phase 1BQ adds a **separately signed candidate registrar enrollment manifest**, **two separately signed offline remote-capture receipts**, exact configured HTTPS-origin and TLS-SPKI-pin comparison, monotonic head/revocation reconciliation and a second one-use server challenge and local audit. These are design and rehearsal controls for future provider integration—**not** network access, a signed live CRL/OCSP, independently retained external head, real eMudhra/CCA authority, actual WORM deletion denial or a witnessed DR restore. Source and signing keys in tests are synthetic and may be controlled by the same fixture operator.

## Engineering details

1. `server/commercialIntegrity/quoteRemoteEvidence.ts` defines exact, bounded canonical Ed25519 registrar and dual-collector receipts with domain-separated signatures, stable SHA-256 manifests and pinned endpoint allowlists. The registrar's candidate signing public key **never arrives inside the packet**; a caller-supplied registrar SPKI must match separately configured `BQ_REGISTRAR_PIN_SHA256`. The two collector keys must have unique Ed25519 SPKI, IDs and PRIMARY/SECONDARY roles, and match operator-configured `BQ_COLLECTOR_PINSET_SHA256`. A registrar-signed candidate enrollment manifest binds quote ID, requested provider, candidate collector pinset and endpoint configuration SHA, policy digest, monotonic candidate epoch, explicit issuance/expiry, `OFFLINE_CANDIDATE_ONLY`.
2. Each offline capture is signed by a distinct pinned collector, bound to the same 5-minute server challenge, registrar manifest, upstream BP candidate packet, BM receipt/source/sequence, expected quote, separately configured `BQ_ENDPOINT_CONFIG_SHA256`, and exact role-specific **canonical HTTPS origin and TLS SPKI hash**. Local tests reject origins using HTTP, embedded credentials, localhost, alternate hostname, non-matching pins, redirects, wrong HTTP status or content type. The `transportMode` is **only** `REPLAY_CAPTURE_ONLY`; no network request occurs, and the TLS-SPKI hash is a claimed value, *not* an observed live TLS handshake. Future actual retrieval must implement independent authenticated client/network controls before this can convey trust.
3. Dual observations must match held local BM signed-candidate receipt SHA and source SHA/sequence, and agree with one another on claimed issuer-chain/CRL/OCSP digest, revocation epoch and `thisUpdate`/`nextUpdate` window; observations/registrar manifests have strict freshness caps. A claimed remote sequence rollback, local lag, revoked/expired candidate key, changed endpoint pin, stale revocation claim or two-source fork is explicitly rejected. A matching claimed digest does not verify an X.509 certificate path or CRL/OCSP signature.
4. Candidate WORM overwrite/delete denial, retention horizon and DR recovered source/sequence/receipt/transcript are checked for two-collector cross-source agreement and held BM source integrity. These are **synthetic reports, not actual provider API calls, Object Lock guarantees or witnessed encrypted restores**.
5. `database/migrations/0040_bq_candidate_remote_evidence.sql` introduces FK-anchored per-quote BQ candidate stream, accepted/incident attempt ledger and server challenge state/consumption. Independent registrar enrollment, genuinely retrieved head, signed live issuer CRL/OCSP, independent WORM and actual witnessed DR **cannot be marked YES**: MySQL `ENUM('NO')` and `ENUM('HOLD')` hard-code trust boundaries. Plain local MySQL is not third-party WORM.
6. `server/commercialIntegrity/quoteRemoteCustody.ts` uses a single transaction/quote parent lock, recomputes quote/BM/BN/BO/BP source integrity, issues random SHA-256 **five-minute one-use challenge** only for a held/consistent BP stream, accepts/rejects bound candidate registrar/collector receipts, and writes only packet/digest metadata. It enforces separate three-way configured root, collector and endpoints fingerprints, exact replay idempotence, rejected duplicate, sticky quarantine for consumed/expired challenge reuse, fork/rollback, signer substitution, changed configured root/transport, revocation regression, remote-head dispute, local source drift or forged stored head/history. No HTTP mutation route, private keys, provider secrets, stock, invoicing, customer quote or PO action.
7. `scripts/migrate-bq-remote-evidence.ts` uses the migration advisory mutex, immutable SHA-256 checksums of all **39** prior SQL migrations, repeat-safe idempotent registration, and refuses prod or non-TLS staging. Only disposable CI (`NODE_ENV=test`, `CRM_TEST_DB=1`, `DB_NAME=aaditech_ci`) or explicitly authorized disposable TLS staging (`STAGING_DISPOSABLE_CONFIRMED=YES`, `aaditech_staging_*`, `DB_SSL=true`, all earlier BM/BN/BO/BP opt-ins plus `BQ_REMOTE_WRITE_APPROVED=YES`) can execute.
8. Old CRM readback remains functional since migration #0040 is installed before existing CRM integration tests.
