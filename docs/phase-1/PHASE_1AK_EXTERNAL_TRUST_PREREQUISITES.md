# Phase 1AK — External Supplier/Warehouse Trust-Anchor Prerequisites, Signed Organizational Claims & Revocation Distribution

**Date: 2026-11-12 | Branch: `chore/phase0-foundation-20261106` | Disposition: PRODUCTION RELEASE HOLD**

## Critical trust boundary

Phase 1AK builds cryptographic **prerequisites**, not an operationally trusted external PKI. No real issuer registry, supplier corporate identity provider, warehouse authority, supplier KYC, issuance acknowledgment, official goods receipt, or externally authenticated signing root has been connected. An OWNER can register an *issuer public-key candidate*, which is just as self-reported as the Phase 1AI public keys. An independently reviewed internal registry reference does **not** prove real organizational authority. A valid signature by this candidate proves only that the corresponding private key signed a canonical message.

Therefore issuer-root status is SQL enum-only **UNVERIFIED**. Organizational authority is SQL enum-only **UNVERIFIED**; stock-posting state remains **DISABLED**. Production approval, live supplier dispatch, official GRN, stock/serial title, accounting/stock posting, reservation, available-to-sell, invoice, payments and warehouse transfer do not become possible. Every Phase 1AG zero-only stock CHECK constraint and Phase 1AH UNPOSTED journal gate remains intact. Phase 1AI/1AJ candidate key proof, review and retirement stay enforced.

## Concrete cryptographic contracts

1. **Issuer candidate.** OWNER with explicit internal supplier/site scope registers a canonical 44-byte Ed25519 X.509/SPKI DER public key, organization registration claim and evidence reference. Only PUBLIC key bytes and SHA-256 fingerprint are stored—never private keys, original confidential documents or corporate account tokens. Same-fingerprint replay is allowed only for byte-identical binding. Independent REVIEWER can mark `REVIEWED_HELD` after inspecting internally provided evidence; this is not a trusted root-of-trust.
2. **Prior source control.** Authority creation requires both the issuer and the candidate key to belong to the same originally registered supplier/site and owner. The candidate key must have passed the Phase 1AI independent key-format review **and** the Phase 1AJ single-use Ed25519 possession challenge with independent reviewer approval. Key retirement or pending rotation immediately denies source use.
3. **Authority signature.** Canonical JSON `aaditech-external-organization-candidate-v1` binds issuer UUID/fingerprint, Phase 1AI key UUID/fingerprint, exact party/site ID, claimed registration, purpose `SUPPLIER_ACK` or `WAREHOUSE_GRN`, validity window and explicit `issuerExternallyAuthenticated:false`, `organizationAuthorityVerified:false`, `officialGrnVerified:false`, `stockPostingState:'DISABLED'`. OWNER obtains exact UTF-8 string via `POST /authority-template` and signs only in an offline environment. Server checks Ed25519 detached 64-byte signature against issuer candidate, exact SHA-256, source, date, correct purpose and pending/retired state before immutable insert. Reviewer recomputes and verifies at decision time.
4. **Revocation distribution.** Canonical `aaditech-candidate-signed-revocation-v1` contains issuer ID/fingerprint, party scope, integer sequence, `issuedAt`, `expiresAt`, sorted unique list of at most 128 lowercase fingerprint SHA-256 values and explicit non-authenticated publisher/disabled posting flags. Signature is a detached Ed25519 64-byte signature over exactly `JSON.stringify(message)` UTF-8 bytes. No feed is fetched from the internet and no external registry is contacted. This is an offline-owner-imported issuer-signed candidate feed.
5. **Anti-rollback / downgrade.** First sequence must be 1; subsequent sequence must be previous+1 under the issuer row lock. Replaying an identical latest signed manifest returns the existing row only if exact SHA and signature match. Mutating a sequence/manifest is conflict. The new revoked set must be a **superset of the previous list**, preventing removal/un-revocation. Issued timestamps cannot be in future (5-minute skew), bundle must not already be expired, and TTL cannot exceed 24 hours. The readiness reader requires the *latest* still fresh feed, re-verifies signature, canonical digest and normalized entries atomically. Missing, expired, corrupt, tampered or revoked key => 409, not a presumed valid status.
6. **Immediate deny-only propagation.** The Phase 1AI `readCandidate()` path now checks current MySQL locking rows in the Phase 1AK revocation table and blocks fingerprints recorded for the same party even when the candidate feed later expires. This is deliberately conservative: no uncertain publisher can *enable* trust or stock, but a locally recorded revocation may *deny* a key. Direct Phase 1AJ emergency retirement and pending rotation also deny usage. A frozen issuer is refused for new claim/feed/attestation checks.
7. **Independent internal attestation.** REVIEWER cannot equal OWNER and must explicitly attest inspection. Positive status remains `REVIEWED_CRYPTO_HELD`. `GET /readiness/:id` is strict: it can acknowledge mathematically consistent *internal* issuer/authority/revocation evidence, but ALWAYS returns `productionReady:false`, `externallyVerified:false`, `officialGrnAuthenticated:false`, and null available-to-sell with concrete hard blockers. No authentic external source has yet been independently established.

## Role/HTTP surface

- OWNER: `GET /api/external-trust/issuers`, `POST /issuers`, `POST /issuers/:id/freeze` (immediate irreversible incident lock), `POST /authority-template`, `POST /attestations`, `GET /attestations`, `POST /revocation-template`, `POST /revocations`, `GET /revocations`, `GET /readiness/:id`, `GET /authority`.
- Independent REVIEWER: `GET /api/external-trust/review/issuers`, `POST /review/issuers/:id/decide`, `GET /review/attestations`, `GET /review/attestations/:id`, `POST /review/attestations/:id/decide`.
- Every route requires session and role, replies no-store. Mutations, including canonical template requests and emergency freeze, require CSRF, recent-password step-up and configured privileged MFA. No route accepts a private key, an external issuer-trust override, an official GRN, inventory posting or supplier PO network dispatch.

The OWNER UI supports issuer candidate registration, previous Phase 1AI candidate UUID binding, canonical offline authority message, signed revocation feed, readiness check and emergency issuer freeze. The REVIEWER UI shows public fingerprints, claimed registration, canonical signed statement, mathematical signature status and independently recorded one-time HELD/reject decisions. All screens explicitly state absence of real external trust.

## External authentication still missing — before any future Phase 1AL activation

The actual external identity/issuer trust onboarding cannot be completed using only owner-entered keys. Before enabling a separate trusted-verification pathway, independently obtain and authenticate legitimate supplier/warehouse organization identities (corporate registry/domain/authorized agents), an **out-of-band pre-established trusted root/pinned certificate controlled outside this app**, signed credential issuance with chain/purpose/expiry, secure supplier/warehouse transport and independently published authenticated revocation distribution (including offline emergency response, rollover, monotonic signed feed history and trust-root compromise). Audit hardware-backed signing and key custody where appropriate. The genuine external PO and source-signed receipt, physical packing/serial/lot QC, official GRN and independent financial controls then require their own workflow and review. A separately change-controlled **operational stock ledger** with reconciled GRN credits, atomic no-negative debits, reservation, serial title/ownership, accounting and reversal policy is still mandatory.

**Release decision: HOLD.** Keep Issue #2 OPEN, Draft PR #1 open/DRAFT/unmerged, `main` untouched. Never issue supplier PO, call vendor, apply production migration, deploy Hostinger, post physical stock, reserve inventory or record financial transactions from this phase.
