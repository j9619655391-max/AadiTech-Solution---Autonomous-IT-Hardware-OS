## Actual Phase 1DM cross-phase identity vulnerability

Phase 1DM verifies registrar and two officer Ed25519 signatures, candidate GitHub logins and exact source/main, then checks the public Phase 1DL terminal receipt. That public report is **correctly redacted**: it has source SHA, base-main SHA and technical status booleans but does **not** carry Security/Business names, the operator's secret session key or the HMAC identifying the exact two users. Thus an applicant could generate an otherwise mathematically valid appointment for *different* usernames on the **same source/main** and pass Phase 1DM using a public Phase 1DL positive receipt that had been obtained by *another reviewer pair*. Neither an Ed25519 signature by a self-supplied registrar root nor a public status boolean proves the nominee identities matched those actually observed by GitHub. This Phase 1DN contract closes that specific technical identity join; the earlier Phase 1DM *standalone candidate-only* result must not be mistaken for the new role-bound cross-phase acceptance.

## Implementation

**`scripts/phase1dn-corporate-role-session-reconciliation.mjs`** exports a pure, offline, deterministic `assessInProcessAppointmentReviewerBinding`. It accepts a Phase 1DM signed candidate packet, two operator-supplied public comparison pins, verification clock, and exactly **seven** fields of the *original in-memory* human-operator 1DL evidence: fresh 32-byte `sessionKey`, first and second exact-head Phase 1CO reviewer observations, actual Phase 1DF role join, pinned base-main Phase 1DG CODEOWNERS result, terminal 1CO nominated reviewer observation, and Phase 1DI terminal governance readback. The candidate's two **signed** Security/Business role logins are the **sole source** for deriving the expected Phase 1DL role-specific HMAC; caller cannot substitute a different pair of nominal logins.

The verifier invokes the existing trusted-in-process **Phase 1DL pure assessor** with all original observations and appointment-derived usernames. The exact role-ordered session HMAC must match the original first/second/terminal 1CO and 1DF HMACs, including real source/main SHA, reviewer permissions, approved current HEAD, pinned effective CODEOWNERS and final policy/review-history consistency. The same newly recomputed Phase 1DL result is then used as input to the existing **Phase 1DM pure Ed25519 candidate assessor**, which separately requires all three mathematically correct signed registrar/officer proofs and strict nonce/expiry/role/registrar-pin shape. Passing **both independently recomputed assessor contracts** is required for a non-authoritative `inProcessCrossPhaseCandidateContractConsistentOnly=true`.

The output has no raw GitHub logins, public-key PEMs, registrar signing keys, nonce, officer challenges, individual HMAC, session key, candidate packet, legal evidence or private-source response. The candidate, source/main SHAs and two assessor-level booleans cannot authorize writes. An unknown/missing operator-session field, altered key, source/main drift, substituted reviewer session, changed role, negative GitHub permission/review/CODEOWNERS/history or bad candidate signature fails closed with fixed diagnostic codes. Actual HTTP GitHub queries are **not executed by this module**, and it is **not an admin or onboarding CLI**. It does not falsely imply caller-provided same-source fake receipts are an independently authenticated GitHub session.

**33 adversarial Node test groups** in `tests/phase1dn-corporate-role-session-reconciliation.test.mjs` use locally generated synthetic Ed25519 signing keys and three signed technical review fixtures. The key regression **first demonstrates that the former Phase 1DM public-boolean gate accepts a fully re-signed alternate Security account with the same HEAD/main**, then verifies that Phase 1DN rejects it by recomputing the original HMAC. Other tests reject re-signed different Business/both officers, swapped Security/Business, cross-session keys/HMACs, omitted review or write-permission observations, altered pinned CODEOWNERS, 1DI revision drift, changed HEAD/main, stale registrar pins, invalid officer signatures, expired candidate, fake GO and any plaintext credential leakage. A positive in-process mathematical join still returns production HARD HOLD and has **zero independent corporate/legal issuer authority**.

The new source and tests are included in both Phase 1BV build-input custody and Phase 1BW review custody source lists. Source and test imports use the existing Phase 1DL and Phase 1DM pure contracts; no extension of GitHub permissions, workflow grants, manager roles or production paths.
